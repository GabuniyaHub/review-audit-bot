# Требования к прототипу репутационного аудита

Дата: 16.10.2026. Основа: документ ВКР и две пользовательские диаграммы.

## Назначение и границы
Telegram-бот помогает владельцу сравнить репутацию одного филиала своей компании с тремя филиалами конкурентов. Анализируются отзывы 2ГИС и Яндекс.Карт. Результат — темы, жалобы, положительные факторы, сравнение и рекомендации с доказательствами. Определение поддельных отзывов не входит в первую версию. REST API для демонстрации — дополнительная функция.

## Пользовательский сценарий
1. `/start` — описание сервиса и начало настройки.
2. `/setup` — своя компания и до трёх конкурентов: название, город, точный адрес, ссылки на карточки обоих источников. Поисковый результат не заменяет подтверждённую карточку филиала.
3. `/settings` — просмотр и изменение набора организаций; отсутствие карточки одного источника явно отмечается.
4. `/report` — создать задачу аудита или выдать существующий отчёт с датой актуальности. Повторная команда не создаёт параллельную копию той же задачи.
5. `/status` — стадия, завершённые источники, ошибки и время последнего обновления.
6. `/help` — команды и объяснение показателей.

Доступ к настройкам и отчётам ограничивается Telegram user ID. Групповые чаты в первой версии не поддерживаются. При недоступности одного источника сохраняется частичный результат с предупреждением; пустая выдача не маскирует ошибку.

## Данные
User, AuditProject, Organization, SourceCard, CollectionRun, Review, ReviewAnalysis, AuditRun, Report.
Отзыв: source, sourceCardId, sourceReviewId (если доступен), text, rating (nullable), publishedAt (nullable), collectedAt, sourceUrl, contentHash. Сохранять исходные и нормализованные даты отдельно, если точная дата неизвестна. Ответы организации не считать отзывами клиентов.
Уникальность: карточка + ID отзыва; при отсутствии ID — детерминированный отпечаток. Между источниками совпадения текста помечать отдельно, не удалять автоматически. Изменённые отзывы повторно анализировать по contentHash. Анализ связывать с версиями модели, промпта и схемы.

## Анализ
Темы: качество продукта/услуги, обслуживание, ожидание, цена, атмосфера, чистота, доступность и прочее. На отзыв допускается несколько тем и смешанная тональность. Оценка в звёздах и тональность текста — разные показатели. LLM возвращает проверяемую структурированную схему и ссылки на ID доказательств; недостоверные ID отклоняются. Текст отзыва — входные данные, а не инструкции модели. Имена авторов не нужны для LLM.
Частоты и доли рассчитывает приложение. Доля темы — число уникальных отзывов с темой / число анализируемых текстовых отзывов организации за одинаковый период. Один отзыв учитывается в теме один раз. Средняя оценка выборки не называется официальным рейтингом площадки. Не вводить непрозрачный общий репутационный балл в первой версии.

## Отчёт
Период и момент сбора; источники и полнота; число оценок и текстовых отзывов; таблица своей компании и трёх конкурентов; распределение тональности; основные жалобы и похвала с частотами; отличия от конкурентов; 3–5 приоритетных действий с ID отзывов и ссылками на карточки. Короткая сводка в Telegram, подробный Markdown-файл. При малой выборке — предупреждение, без уверенных ранжирований. Ограничения источников видны пользователю.

## Фоновые задачи
Планировщик NestJS запускает обновление ежедневно; время настраивается. Задания сохраняются в PostgreSQL; после перезапуска видны незавершённые задачи. Ограничение параллелизма, тайм-ауты, конечное число повторов с задержкой. CAPTCHA/403/429 и изменение разметки — отдельные ошибки. Не повторять запросы бесконечно. Уведомления об одном и том же сбое объединяются.

## Критерии приёмки
- Своя компания и три конкурента сохраняются; данные двух пользователей не смешиваются.
- Повторный сбор той же выборки не увеличивает число одинаковых отзывов.
- Сбой одного источника даёт частичный отчёт; полная недоступность не превращается в успешный пустой аудит.
- Выводы и рекомендации ссылаются на существующие отзывы; числа воспроизводимы без LLM.
- Секреты вне Git; в журналах нет токенов и полных приватных сообщений.
- Не менее 500 уникальных текстовых отзывов суммарно по четырём филиалам; стремиться минимум к 100 на организацию. Если данных меньше — явно указать.
- Замер холодного цикла (сбор + анализ + отчёт) и повторного отчёта отдельно. 10 минут — проверяемый целевой показатель, не обещание.
- Ручная разметка 100 отзывов, стратифицированных по компании, источнику и оценке: macro-F1 тональности, precision/recall тем; отдельно проверка доказательств рекомендаций. Порог качества согласовать до подбора промптов. Зафиксировать стоимость, ошибки, полноту и ограничения выборки.

## Предварительная архитектура
NestJS + TypeScript, PostgreSQL, отдельные адаптеры источников, семантический анализ через LLM API. Сборщик можно запускать отдельным Python-процессом с JSON-контрактом и ограничениями времени/памяти; Python не меняет основной стек ВКР. Не требуется сразу Redis или Docker. Действующие сайты не затрагивать; ресурсы сервера оценить перед размещением.
