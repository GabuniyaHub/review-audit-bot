# Этап 3: Telegram-интерфейс и настройка проекта

Дата: 16.10.2026. Реализован код Telegram-интерфейса. Живой токен не предоставлялся, поэтому проверка с настоящим ботом ещё не выполнялась. Автоматические проверки используют настоящий временный PostgreSQL и подставной Telegram API; сообщения людям не отправлялись.

## Команды и сценарий
- `/start`, `/help` — назначение и список команд.
- `/setup` — черновик настройки: название своей компании, город, точный адрес, ссылка 2ГИС, ссылка Яндекс.Карт. «-» пропускает площадку; минимум одна карточка обязательна.
- `/add` — добавить конкурента после заполнения организации, максимум три.
- `/done` — завершить добавление раньше и посмотреть сводку. После третьего конкурента сводка открывается автоматически.
- `/save` — применить сводку. До подтверждения прежние настройки действуют.
- `/resume` — повторить текущий вопрос; черновик хранится в PostgreSQL и сохраняется после перезапуска.
- `/cancel` — отменить только черновик.
- `/settings` — собственные сохранённые компании и карточки.
- `/status` — собственный последний аудит или честное сообщение, что аудит ещё не запускался.
- `/report` — собственная последняя сохранённая сводка. Если её нет, бот сообщает о неподключённых сборе и анализе; пустой незавершаемый аудит не создаёт. Запуск конвейера относится к последующим этапам.

Повторная настройка создаёт новую версию проекта и переключает текущий профиль; старые организации, аудиты и отчёты сохраняются в БД. В интерфейсе отображается только текущая версия. Выбор старых версий и выгрузка полного отчёта будут добавляться вместе с отчётами. Проект можно сохранить с одним основным филиалом и 0–3 конкурентами; для эксперимента ВКР нужно заполнить все три.

## Ссылки и разделение данных
Принимаются HTTPS-ссылки на отдельную карточку с числовым ID (до 20 цифр) на разрешённых доменах 2gis.ru, yandex.ru, yandex.com, включая www. Ссылки поиска, сети, посторонние домены, логин/пароль в URL и нестандартный порт отклоняются. Короткие ссылки нужно предварительно раскрыть в браузере. Query-параметры и трекинг не сохраняются. Ссылки не запрашиваются по сети на этапе настройки. Разные организации не могут использовать одну и ту же карточку одной площадки внутри черновика.

Карточки сохраняются как unverified: соответствие адреса и организации ещё должен подтвердить сборщик/пользователь. Наличие валидной ссылки не считается проверкой филиала.

Обрабатываются только личные сообщения, где chat.id совпадает с from.id; сообщения групп, каналов и ботов не читают и не меняют проекты. Внешнего HTTP-метода приёма updates нет. Владелец определяется из Telegram update, а не из текста команды. Настройки, статусы и отчёты выбираются по владельцу текущего профиля. В БД добавлена составная связь проекта с пользователем.

## Надёжность
Миграция `002_telegram` добавляет профили, черновики, входящие идентификаторы updates, очередь ответов и offset. Миграция `001_initial` не изменена. Обработка update, шаг диалога и запись ответа выполняются в одной транзакции. Повтор одного update_id для одного bot_id не меняет настройки повторно. Действия пользователя сериализуются транзакционной блокировкой.

Long polling использует стандартный Telegram Bot API. Перед запуском проверяются getMe, отсутствие webhook и готовность базы. Настроенный webhook автоматически не удаляется. Отдельная PostgreSQL-блокировка не допускает второго экземпляра poller для того же бота в той же базе. При внешнем конфликте 409 или недействительном токене 401 poller останавливается и готовность сервиса меняется на 503. Нельзя запускать этот же токен параллельно с другим сервисом, использующим другую базу: БД-блокировка в таком случае не общая.

Ответы сохраняются до отправки. Ошибки доставки имеют конечное число попыток (до пяти); 400/403 считаются постоянной ошибкой, 429 учитывает retry_after. Старый отложенный ответ не обгоняется более новым. Offset сохраняется после обработки update. При аварии после приёма сообщения Telegram, но до отметки sent в БД возможна повторная отправка ответа — exactly-once доставка наружу не гарантируется. Накопленные входящие ID и записи ответов потребуют политики хранения перед промышленным запуском.

SIGTERM/SIGINT отменяют текущий сетевой запрос и завершают poller до закрытия пула. Токен отсутствует в журналах и текстах ошибок; запросы к Telegram не используют HTML/Markdown parse_mode, пользовательский текст не интерпретируется как разметка. Предпросмотр ссылок отключён.

## Подключение живого бота
1. Получить токен своего бота через BotFather.
2. Записать его только в локальный `.env` или секрет окружения, не в Git и не в README.
3. Настроить DATABASE_URL и применить `npm run db:migrate`.
4. Установить `TELEGRAM_ENABLED=true` и `TELEGRAM_BOT_TOKEN=<свой токен>`.
5. Запустить `npm start`, затем написать своему боту `/start`.

При отключённом Telegram токен не требуется. Включённому poller нужно минимум два соединения БД; рекомендуемый DB_POOL_MAX=5. Тесты должны запускаться с Telegram, отключённым в обычной точке входа; реальный API в них заменяется тестовым.

Документация протокола: https://core.telegram.org/bots/api#getupdates и https://core.telegram.org/bots/api#sendmessage.

## Проверки
`npm test`: конфигурация, разрешённые ссылки, защита от подмены домена и неверного ID, шаги настройки, обязательная карточка, повтор карточки, лимит конкурентов, секреты и ошибки API.

`npm run test:integration`: миграции и прежние проверки этапа 2; сохранение черновика и восстановление сервисом, две независимые учётные записи, недоступность данных в группе, отмена без потери настройки, повтор update без дублей, настройка всех трёх конкурентов, доступ к отчёту только владельцу, отсутствие фиктивного аудита, повтор доставки, запрет второго poller и отказ при настроенном webhook. PostgreSQL изолирован, Telegram API подставной.
